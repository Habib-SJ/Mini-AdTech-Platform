## تصمیمات معماری و طراحی سیستم
این سند، انتخاب‌های کلیدی معماری و محدودیت‌های ایجاد شده در طول توسعه‌ی MVP پلتفرم Mini AdTech را تشریح می‌کند.


1- برای کاهش پیچیدگی در نسخه MVP، سیستم فرض می‌کند هر ناشر تنها یک سایت و بدون مفهوم AdSlot دارد؛ این تصمیم باعث افزایش سرعت توسعه شده اما انعطاف‌پذیری چیدمان را محدود می‌کند.

2- گزارش‌دهی فعلاً مستقیماً از جداول خام انجام می‌شود که ریسک مقیاس‌پذیری دارد؛ لذا برنامه‌ریزی شده تا برای حل این مشکل از Celery برای تجمیع (Aggregation) استفاده شود.

3- جهت جلوگیری از مصرف بیش از حد بودجه در درخواست‌های هم‌زمان، از select_for_update و تراکنش‌های atomic برای تضمین صحت داده‌ها استفاده شده است.

4- برای جلوگیری از کلیک‌های جعلی، رابطه یک‌به‌یک بین نمایش و کلیک با استفاده از OneToOneField و چک کردن exists() برقرار شده که خط دفاع اصلی در برابر تزریق کلیک‌های تکراری است.

5- برای جلوگیری از حملات Replay، درخواست‌های کلیک با استفاده از TimestampSigner و با انقضای یک‌ساعته امضا می‌شوند تا از صحت زمان و محتوای کلیک اطمینان حاصل شود.

6- شناسایی IP کاربر بر اساس هدر X-Forwarded-For انجام می‌شود، با این فرض که سیستم پشت یک پروکسی قابل اعتماد قرار دارد.

7- فرآیند انتخاب تبلیغ با استفاده از values_list و random.choice انجام می‌شود؛ در این مرحله برای حفظ سرعت، از الگوریتم‌های پیچیده رتبه‌بندی (Ranking) یا هدف‌گیری (Targeting) صرف‌نظر شده است.

8- جهت جلوگیری از لو رفتن وضعیت داخلی سیستم، برای ناشران مسدود شده در نقاط دسترسی عمومی، به جای کد ۴۰۳، پاسخ ۴۰۴ ارسال می‌شود.

9- کلیک‌های ناشران مسدود شده، جهت بررسی ثبت (Log) و برچسب‌گذاری می‌شوند اما در محاسبات تسویه حساب لحاظ نمی‌شوند تا هم داده‌ها حفظ شوند و هم از پرداخت‌های غیرمجاز جلوگیری شود.

10- شماره کارت‌های بانکی در این نسخه به صورت متن ساده ذخیره می‌شوند که این یک محدودیت است و در نسخه عملیاتی نیاز به رمزنگاری پیشرفته دارد.

11- زیرساخت از Neon برای مدیریت PostgreSQL استفاده می‌کند، اما به دلیل محدودیت‌های محیطی، استفاده از Docker و Redis در این مرحله نهایی نشده است.
